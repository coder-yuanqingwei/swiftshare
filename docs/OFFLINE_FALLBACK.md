# 无 WiFi 场景的传输兜底：设计分析

本文回答一个问题：**两台设备没有共同 WiFi 时怎么办，能不能回落到蓝牙？**
结论基于当前代码实际实现，不是泛泛而谈。

## 一、问题定义

「没有 WiFi」实际包含三种不同情况，需要分开处理：

| 情况 | 描述 | 现有代码能否工作 |
|---|---|---|
| A. 无外部 WiFi，但可开热点 | 两台手机都在户外/无路由器环境 | **能**，一台开热点另一台加入即可，属同一局域网 |
| B. 完全无任何局域网 | 例如飞行模式，仅留蓝牙 | **不能**，HTTP 无处可连 |
| C. 有 WiFi 但拿不到 IP | NetInfo 返回 0.0.0.0、连的是蜂窝等 | 部分处理，`network.ts` 有兜底但仍会抛错 |

用户的「回落到蓝牙」诉求主要对应情况 B。

## 二、当前架构的真实边界

阅读 `app/src/services/ble.ts` 后需要明确一点：

> **当前 BLE 只有「控制面」，没有「数据面」。**

GATT 服务 `0000fff0` 下只注册了两个特征：

- `HANDSHAKE`（Read + Notify）：承载几十字节的
  `{ ip, port, token, device_name }` JSON，由 `publishHandshake()` 写入、
  发送方 `readHandshake()` 读取。
- `CONTROL`（Write）：承载 `ACK` 这类短控制指令，由 `sendControl()` 写入。

文件字节全部经由 `transfer.ts → send_files()` 走 Rust axum HTTP 服务，
依赖 TCP/IP 局域网。`ble.ts` 顶部注释也明确写了「BLE only carries the tiny
control-plane payload … All file bytes go over WiFi」。

因此「回落到蓝牙」**不是打开一个开关**：需要新建 GATT 数据特征 + 应用层的
分块、序号、重传、校验、重组协议，是一整条数据通道的开发量。

## 三、技术约束（为什么蓝牙兜底有限）

### 1. iOS 经典蓝牙不可用

经典蓝牙的 SPP / RFCOMM 串口协议在 iOS 上需要 **MFi 认证**（Made for iPhone），
普通第三方 App 无法使用。所以跨 Android↔iOS 的蓝牙路径只剩 **BLE (GATT)**。

### 2. BLE 吞吐是硬限制

- 链路层每个连接的 ATT MTU 默认 23 字节，协商后 iOS 通常约 185 字节、
  Android 约 512 字节（部分可到 517）。
- 逐包 `writeWithoutResponse` / `notify`，加上 iOS 后台连接间隔与系统调度，
  实际有效吞吐大致在 **20–100 KB/s** 量级（真机需实测，不同机型差异大）。

按此估算：

| 内容 | 大小 | 预计 BLE 耗时 |
|---|---|---|
| 一段文字 / 联系人 | 几 KB | 秒级，可接受 |
| 一张压缩照片 | 约 3 MB | 约 1–3 分钟 |
| 一段短视频 | 约 100 MB | 30 分钟以上，不可用 |

BLE 适合应急传小对象，不适合本产品定位的图片/文件主场景。

### 3. 平台原生近场方案不能跨平台

- AirDrop：仅 Apple 设备之间。
- Quick Share（原 Nearby Share）：仅 Android 设备之间。
- MultipeerConnectivity（Apple AWDL）：主要 Apple 生态，Android 侧无对等实现。

对「Android ↔ iPhone 互传」这个核心需求，三者都帮不上忙。

## 四、三种方案对比

| 方案 | 跨 Android↔iOS | 速度 | 改造量 | 适用 |
|---|---|---|---|---|
| BLE 数据兜底 | ✅ 唯一跨平台蓝牙路径 | 20–100 KB/s | 大：新数据通道 + 协议 | 应急小文件 |
| 热点组网 | ✅ | 走现有 HTTP，几十 MB/s | 小：补检测与引导 UI | **推荐，主兜底** |
| 平台原生近场 | ❌ 各自封闭 | 快 | — | 仅同生态 |

## 五、推荐方案：热点组网作为主兜底

核心思路：**不去重造一条慢速蓝牙数据通道，而是让两台设备形成一个局域网**，
从而复用已经跑通的 HTTP 高速传输。代码侧已经有基础：

- `network.ts` 的 `getLocalIp()` 已经把 `RNFS.getIPAddress()` 作为兜底来源，
  其注释明确提到「when the phone is the hotspot host」的场景。
- `HomeScreen.tsx` 已有提示文案：「两台设备需连接同一 WiFi，或一台开热点另一台加入」。
- `network_security_config.xml` 已放行局域网明文 HTTP。

缺的主要是**主动检测 + 清晰引导 + 失败提示**，而不是传输层改造。

### 建议的改造点（后续实现时）

1. **网络可用性检测**
   在接收方 `startReceiver()` 之前调用 `getLocalIp()`；失败时不是直接抛错，
   而是进入「热点引导」状态。

2. **接收方 UI 分支**
   检测到无局域网时，展示三步引导：
   1. 打开本机个人热点；
   2. 让发送方加入该热点；
   3. 点击「已就绪」后重新取 IP 并生成握手/QR。

3. **发送方连接校验**
   发送方拿到握手后，先用 `/status`（Rust 引擎已有）做一次连通性探测，
   不通则提示「确认两台设备在同一个 WiFi 或热点下」，而不是直接报上传失败。

4. **iOS 个人热点的注意点**
   - iOS 作为热点主机时，其可被访问的局域网地址通常是 `172.20.10.1`
     网段，但 iOS App 通过公开 API 拿这个地址不一定可靠，需要真机验证
     `NetInfo` / `RNFS.getIPAddress()` 在热点 host 模式下的返回值。
   - 若取不到，退而求其次：让**发送方开热点、接收方加入**，此时接收方是普通
     STA，能稳定拿到 IP，流程更可靠。引导 UI 应覆盖两种方向。

5. **不需要改的部分**
   Rust HTTP 引擎、BLE 握手、QR 码、SHA256 校验、断点重传（当前若有）均保持原样。

### 验收标准

- 两台设备均无任何外部 WiFi 时，仅靠一台开热点即可完成图片/文件互传，
  吞吐与同 WiFi 场景一致。
- 失败时给出明确的「检查热点/WiFi」指引，而不是笼统的网络错误。

## 六、BLE 数据兜底（可选的最后手段）

仅当热点也不可用时启用，定位为「应急通道」，建议加开关与明确的速度预期提示。

需要新增的设计要点：

1. **新 GATT 数据特征**：例如 `DATA`（WriteWithoutResponse）+ `DATA_ACK`（Notify），
   MTU 协商后按分片大小切块。
2. **分块协议**：每帧含 `session_id / chunk_index / total_chunks / payload`，
   接收方按序号重组，缺失帧请求重传。
3. **校验**：沿用 Rust 侧的 SHA256，文件重组完成后校验完整性。
4. **限制**：建议单文件上限（如 5–10 MB）、总会话超时、仅允许图片等小文件，
   并在 UI 明确告知「蓝牙很慢，仅用于小文件应急」。
5. **与现有握手的关系**：握手仍走原 `HANDSHAKE` 特征，BLE 数据通道独立，
   不在原特征上叠加大数据，避免破坏现有发现/握手流程。

风险：iOS 后台 BLE 传输可能被系统挂起；不同机型 MTU/连接参数差异导致的
实际吞吐不稳定；跨 Android↔iOS 的 peripheral/central 角色兼容性需真机充分验证。

## 七、结论与优先级

1. **优先做热点组网引导**——改动小、速度快、覆盖绝大多数「没 WiFi」场景。
2. **BLE 数据兜底排后**——作为无网络时的最后手段，且要限制文件类型与大小。
3. 当前代码已经具备热点组网的底层能力，主要工作在产品引导层。

> 本文仅为设计分析，未改动任何运行时代码。
